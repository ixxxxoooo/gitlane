# 0003 撤销基于引用快照与文件快照

日期:2026-11-04 · 状态:已采纳

## 背景

方案要求 checkout、commit、discard、删除分支、reset 等操作都能一键撤销与重做,且不能丢数据。

## 决定

所有写操作经命令层执行,执行前后各拍一次快照,撤销 = 恢复“前”,重做 = 恢复“后”。

- **引用快照**(`RefSnapshot`):HEAD 指向(分支 / 分离 / 未出生)+ 全部 `refs/heads/*`、`refs/tags/*`。
  恢复顺序:先改未检出的引用 → 处理 HEAD(同一分支用 `reset`,换分支用 `checkout`)→ 再改原先检出的分支。
  同一分支移动时的 reset 方式随命令类型记录:commit 用 soft(改动回到暂存区),reset 用原方式,
  cherry-pick / revert / merge / pull 用 keep(保留不冲突的本地改动)。
- **工作区改动**:hard reset 前用 `git stash create` 生成一个不改变工作区的 stash 提交,撤销时
  `reset --hard` 回原提交后 `git stash apply --index` 应用回来。
- **文件快照**(`FileSnapshot`):丢弃前把文件当前内容写入对象库(blob),撤销时写回;文件原本不存在则删除。
- **只恢复记录本身改过的东西**:恢复时只动前后快照之间不同的引用、HEAD 与上游配置,其余保持现状。
  否则自动 fetch 带回的新标签、之后新建的分支,会在撤销更早的操作时被一起删掉。
- **恢复前先核对**:要动的每个引用、HEAD、文件,必须还停在操作后的状态(或已经是目标状态,
  即上次恢复做到一半);否则说明之后别处改过(终端里提交、切分支、丢弃后又改文件),报错不动,
  避免把新提交从分支上拿掉或覆盖新改动。
- **上游配置**:`git branch -d` / `-m` 会连带删除或改名 `branch.<name>.remote/merge`,
  引用快照里一并记下,撤销删除 / 重命名分支时恢复跟踪关系。
- **hard reset 的工作区**:撤销前工作区有已跟踪文件的改动则拒绝(撤销要 `reset --hard`,会冲掉它们);
  重做前重新 `stash create` 一份当时的改动,替换记录里的 `wip_before`,下次撤销拿回的是最新的改动。
- **删除 stash**:记下 stash 提交与描述,撤销用 `git stash store` 放回列表顶部,重做按提交找到它再删。
- **撤销提交**时把提交信息放回提交框(框里已经有字就不覆盖)。
- 文件快照存原始字节(不经 autocrlf 等过滤器)与可执行位,写回后与丢弃前完全一致。
- 前后快照相同的记录不入栈;撤销或重做失败时记录放回原栈。
- 撤销栈只在内存中,每仓库上限 100 条。

## 不覆盖

stage / unstage(本身就能反向操作)、stash push / apply / pop(改动不会丢)、fetch、
push(远程的变化无法本地撤销)、中止 merge / rebase(执行前确认,列出会丢掉解决结果的文件)。

## 风险与对策

每类操作在 `gitcore/tests/repo_ops.rs` 单独写撤销测试;hard reset、force push、丢弃改动执行前弹确认框并列出影响范围。
